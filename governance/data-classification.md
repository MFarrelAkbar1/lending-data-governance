# Data Classification

Every source column carries `classification`, `pii`, `pdp_category`, `data_owner` and `data_steward` in its dbt `meta` (generated by `dbt_project/scripts/generate_sources.py`, visible in the dbt docs catalog). Mart columns carry `classification` and `pii` too.

## Levels

| Level | Definition | Handling rules | Examples in this dataset |
|---|---|---|---|
| **Public** | Approved for anyone, no harm if disclosed | No restriction | Aggregated DQ scores, the data dictionary, this repository's documentation. No row-level column is Public. |
| **Internal** | For employees; low harm if disclosed, not about an identifiable person | Company systems only; no external sharing without approval | Normalized building statistics (`APARTMENTS_AVG`), document flags (`FLAG_DOCUMENT_3`), process time (`HOUR_APPR_PROCESS_START`), audit columns (`_batch_id`) |
| **Confidential** | Personal data or identifiers of a customer; harm if disclosed | Role-based access; masked in non-production; logged access; shared only on need-to-know | IDs (`SK_ID_CURR`, `SK_ID_PREV`), demographics (`CODE_GENDER`, `DAYS_BIRTH`, `NAME_FAMILY_STATUS`), employment, region, previous application attributes |
| **Restricted** | Personal financial data, credit outcomes and scores; serious harm if disclosed | Named-user access approved by the data owner; encryption at rest; no copies to desktops or email; masked or aggregated for analytics | Amounts (`AMT_INCOME_TOTAL`, `AMT_CREDIT`), `TARGET`, external scores (`EXT_SOURCE_*`), all bureau, bureau balance and installment payment history |

## Rules used to classify (from the generator)

1. Audit columns (`_loaded_at`, `_source_file`, `_batch_id`): Internal, not PII.
2. `SK_ID_*` identifiers: Confidential, PII. They are pseudonymous, but linkable to a person inside the company, so they are still personal data.
3. Restricted, PII: anything in `bureau`, `bureau_balance` and `installments_payments`; any `AMT_*`, `RATE_*`, `EXT_SOURCE_*`, `OBS_*`, `DEF_*` column; `TARGET`; credit decision fields of previous applications (status, reject reason, term, yield group).
4. Confidential, PII: application columns that describe the person (demographics, family, education, employment, phone and email flags, region), and the remaining previous application attributes.
5. Internal, not PII: everything else in `application_train` (building statistics, document flags, process timing, contract type).

## Personal data under UU PDP (learning reference, not legal advice)

UU No. 27 Tahun 2022 tentang Pelindungan Data Pribadi splits personal data into two groups. The `pdp_category` meta maps columns to them:

- **Specific personal data** (Pasal 4 ayat 2), which includes *data keuangan pribadi* (personal financial data): all 53 Restricted columns, for example income, credit amounts, repayment history, bureau records and the default flag.
- **General personal data** (Pasal 4 ayat 3), which includes gender, marital status and data that can be combined to identify a person: the 64 Confidential columns, including the pseudonymous IDs.
- No direct identifiers (name, NIK, phone number, address) exist in this public dataset; the IDs are already recoded by the data provider.

## How classification connects to access control

In a production setup, the meta would drive policy instead of being documentation only: for example a dbt `post-hook` or a catalog tool (OpenMetadata, DataHub) reads `classification` and applies column masking or grants (Restricted columns visible only to roles approved by the data owner). This project stops at tagging; it does not enforce access.
